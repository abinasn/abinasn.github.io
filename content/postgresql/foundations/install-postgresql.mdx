## Definition

Installing PostgreSQL means producing three separate things on a machine.

| Part | What it is | Exists until |
|---|---|---|
| Program files | The executables, including `postgres` (the server itself) and small helper tools | Uninstalled |
| Data directory | One folder on disk holding every database, table, and log the server manages | Deleted |
| Server process | The running `postgres` program, listening on a port | Stopped |

A **port** is a numbered entry point on a machine that a program listens on. Other programs connect by naming the machine and the port. PostgreSQL listens on port **5432** by default.

"Installed" and "running" are different states. A machine with program files and a data directory, but no process, accepts no connections.

Installation, data directories, and ports are specific to PostgreSQL as a product. The SQL standard does not define how a server is installed or run.

## How it works

### Trace 1 — Homebrew on macOS

**Homebrew** is a package manager for macOS: a command-line tool that downloads, installs, and updates software. **`pg_isready`** is a helper program that attempts a connection and reports whether a server answered. It does not log in.

| Step | Command | Program files | Data directory | Process | `pg_isready` reports |
|---|---|---|---|---|---|
| 0 | none | no | no | no | command not found |
| 1 | `brew install postgresql@18` | yes | yes | no | `no response` |
| 2 | `brew services start postgresql@18` | yes | yes | yes | `accepting connections` |
| 3 | `brew services stop postgresql@18` | yes | yes | no | `no response` |
| 4 | `brew services start postgresql@18` | yes | yes | yes | `accepting connections` |

Step 1 builds the data directory by running **`initdb`**, a one-time program that creates the folder structure and a first **superuser** — an account permitted to do everything. On Homebrew, that superuser is named after the macOS login account.

Step 3 removes only the process. Every file created in step 1 remains, so step 4 resumes with the same data.

The data directory after step 1, partial listing:

```
/opt/homebrew/var/postgresql@18/
├── base/             table data, stored as ordinary files
├── pg_wal/           write-ahead log
├── postgresql.conf   server settings, including the port
└── pg_hba.conf       rules for which clients may connect
```

The **write-ahead log** (WAL) is a record of every change, written before the change reaches the table files, so a crash can be recovered from it. It lives inside the data directory, which is why the data directory alone is enough to restart a server with nothing lost.

### Trace 2 — Docker

**Docker** runs software inside a **container**: an isolated process with its own private filesystem. A container is created from an **image**, a read-only snapshot of program files. One image can produce many containers.

The official `postgres` image checks the data directory at every container start:

| Start | Data directory at start | `initdb` runs? | `POSTGRES_PASSWORD` used? |
|---|---|---|---|
| First `docker run` | empty | yes | yes — becomes the password of superuser `postgres` |
| `docker stop`, then `docker start` | populated | no | no |
| Container removed, new `docker run` on the same volume | populated | no | no — the original password stays |

Configuration variables take effect only on the first start. Changing the password variable later changes nothing, because `initdb` never runs again on a populated directory.

A **volume** is storage managed by Docker that exists outside any container. Placing the data directory in a volume lets the data survive removal of the container.

| Image | Data directory inside the container | Where a volume must be mounted |
|---|---|---|
| `postgres:17` and earlier | `/var/lib/postgresql/data` | `/var/lib/postgresql/data` |
| `postgres:18` | `/var/lib/postgresql/18/docker` | `/var/lib/postgresql` |

On an 18 image, a volume mounted at the older path stays empty. The data lands in an unnamed volume instead, which no future container reuses.

### Trace 3 — two servers, one machine

A container has its own set of ports. The option `-p HOST:CONTAINER` forwards a port on the machine to a port inside the container.

| Server | Listens at | Reached from the machine at |
|---|---|---|
| Homebrew | 5432 | `localhost:5432` |
| Docker with `-p 5433:5432` | 5432, inside the container | `localhost:5433` |
| Docker with `-p 5432:5432` | 5432, inside the container | conflict — 5432 is already held |

A port on an address serves one listener. A second server requesting the same port either fails to start or, depending on how each binds, leaves clients reaching a different server than intended.

## Implementation

Homebrew marks versioned formulas **keg-only**: installed, but not added to `PATH` (the list of folders a shell searches for commands). This lets several major versions coexist on one machine.

```bash
# Homebrew — macOS on Apple Silicon
brew install postgresql@18

# Put the keg-only commands on PATH
echo 'export PATH="/opt/homebrew/opt/postgresql@18/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

brew services start postgresql@18   # start now, and at every login
pg_isready                          # /tmp:5432 - accepting connections
brew services stop postgresql@18    # end the process; the data directory stays
```

```bash
# Docker
docker run -d --name pg18 \
  -e POSTGRES_PASSWORD=change-me \
  -p 5433:5432 \
  -v pgdata18:/var/lib/postgresql \
  postgres:18

pg_isready -h localhost -p 5433     # localhost:5433 - accepting connections
docker stop pg18                    # end the process; the volume keeps the data
docker start pg18                   # resume with the same data
```

| Option | Effect |
|---|---|
| `-d` | Run in the background |
| `--name pg18` | A fixed name for later `stop` and `start` |
| `-e POSTGRES_PASSWORD=...` | Superuser password; the image refuses to initialise an empty directory without one |
| `-p 5433:5432` | Machine port 5433 forwards to container port 5432 |
| `-v pgdata18:/var/lib/postgresql` | The data directory lives in the named volume `pgdata18` |
| `postgres:18` | Image name, pinned to major version 18 |

Both methods pin the major version: `@18` in the formula name, `:18` in the image tag. A data directory is tied to the major version that created it, so an unpinned update can leave a newer server unable to read an older directory.

## The invariant

**The data directory is the database; the process only serves it.**

| Action | Process | Data directory | Data kept |
|---|---|---|---|
| Stop the service or container | ends | untouched | yes |
| Start it again | reads the same directory | untouched | yes |
| Remove a container whose data is in a named volume | ends | untouched, in the volume | yes |
| Remove a container whose data is in an unnamed volume | ends | no longer reachable | no |
| Delete the data directory | cannot start | gone | no |

The cost is placement. The data directory must sit somewhere that outlives the process: a fixed folder for Homebrew, a named volume for Docker. Each running server also needs a port no other server holds, and every client must name that port.

## TL;DR

- Installing PostgreSQL produces program files, a data directory, and — once started — a server process; only the process answers connections.
- `initdb` builds the data directory once: Homebrew runs it during install, the Docker image runs it on the first start with an empty directory.
- Stopping the server ends the process and leaves every file of the data directory on disk.
- Docker preserves data only when the data directory is in a named volume; for `postgres:18` the volume mounts at `/var/lib/postgresql`.
- One port serves one server: a second local server needs its own port, such as 5433.
- `pg_isready` reports whether a server accepts connections without logging in.
