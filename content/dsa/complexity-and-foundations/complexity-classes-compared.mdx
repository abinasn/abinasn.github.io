## Definition

A **complexity class** is a growth rate that describes how an algorithm's work scales with input size — O(1), O(log n), O(n), O(n log n), O(n²), O(n³), O(2ⁿ), O(n!).

Deriving which class an algorithm belongs to is one skill. Judging whether that class is fast enough for a given input size is a separate one, and it is the subject here.

## The problem it solves

An algorithm's class alone does not say whether it will finish in time. O(n²) is instant on a hundred items and hopeless on a million.

Without a way to convert a class plus an input size into an estimated running time, the only way to find out is to write the code and wait.

## How it works

### The gap between classes is not a fixed tax

Compare an O(n) algorithm against an O(n²) one at two input sizes:

| n | O(n) does | O(n²) does | O(n²) is slower by |
|---|---|---|---|
| 10 | 10 | 100 | 10× |
| 10,000 | 10,000 | 100,000,000 | 10,000× |

At ten items the quadratic algorithm does ten times the work. At ten thousand items it does ten thousand times the work.

The penalty is not a constant multiplier that can be absorbed by faster hardware. It grows with the input, which is why a poor complexity class can pass every test on small data and fail on production-sized data.

### The anchor: 10⁸ operations per second

A rough but reliable figure for typical hardware: **about 10⁸ (100 million) simple operations take about one second.** A simple operation here means an array access, a comparison, or an arithmetic step.

This figure is empirical, not derived — it comes from how fast processors execute instructions. Everything below is worked out from it.

Applying it to the table above, at n = 10,000:

| Algorithm | Operations | Time |
|---|---|---|
| O(n) | 10⁴ | 10⁴ ÷ 10⁸ = 0.0001 s |
| O(n²) | 10⁸ | 10⁸ ÷ 10⁸ = 1 s |

Same problem, same input, and one version is ten thousand times slower in wall-clock terms.

### The ladder at real input sizes

Operation counts for each class, computed at five input sizes:

| n | O(log n) | O(n) | O(n log n) | O(n²) | O(n³) | O(2ⁿ) |
|---|---|---|---|---|---|---|
| 10 | 3 | 10 | 33 | 100 | 1,000 | 1,024 |
| 100 | 7 | 100 | 664 | 10,000 | 10⁶ | 1.3 × 10³⁰ |
| 1,000 | 10 | 1,000 | 9,966 | 10⁶ | 10⁹ | beyond counting |
| 100,000 | 17 | 10⁵ | 1.7 × 10⁶ | 10¹⁰ | 10¹⁵ | beyond counting |
| 1,000,000 | 20 | 10⁶ | 2.0 × 10⁷ | 10¹² | 10¹⁸ | beyond counting |

Two things stand out.

O(log n) barely moves. Going from n = 10 to n = 1,000,000 — a hundred-thousand-fold increase — takes it from 3 operations to 20.

O(2ⁿ) is finished by n = 100. At 1.3 × 10³⁰ operations it would run for longer than the age of the universe, so exponential growth is not a matter of being slow but of being impossible past a small threshold.

### Reading the ladder backwards

The same anchor answers the more useful question: given an input size, which classes are affordable? Each entry below is the largest n that finishes in roughly one second.

| Class | Largest n in ~1 second | Typical shape |
|---|---|---|
| O(1) | no limit | direct formula, hash lookup |
| O(log n) | no limit | binary search on sorted data |
| O(n) | 100,000,000 | single pass over the input |
| O(n log n) | ~4,500,000 | sorting, or sort then scan |
| O(n²) | 10,000 | nested loop over all pairs |
| O(n³) | 464 | three nested loops |
| O(2ⁿ) | 26 | enumerate every subset |
| O(n!) | 11 | enumerate every permutation |

The last two cutoffs are sharp. 2²⁶ ≈ 6.7 × 10⁷ finishes in well under a second, while 2³⁰ ≈ 1.1 × 10⁹ takes about eleven. 11! ≈ 4.0 × 10⁷ is fine; 12! ≈ 4.8 × 10⁸ is roughly five seconds.

### Worked example: reading a constraint

A problem states that the input string has length n ≤ 3,000. Test the candidate classes against the table:

| Class | Operations at n = 3,000 | Time | Verdict |
|---|---|---|---|
| O(n²) | 9 × 10⁶ | 0.09 s | fits comfortably |
| O(n³) | 2.7 × 10¹⁰ | 270 s | far over budget |

The constraint is doing more than bounding memory — it is narrowing which solutions can work. A limit of 3,000 rules out the triple loop and leaves the quadratic one, so an O(n²) approach is likely what the problem expects.

The same reading applies across the range: n ≤ 10⁵ points to O(n) or O(n log n); n ≤ 1,000 permits O(n²); n ≤ 20 signals that an exponential search over subsets is the intended answer rather than something to be avoided.

## The invariant

The running time of an algorithm is its operation count at the given input size divided by roughly 10⁸ per second — so a complexity class is never fast or slow on its own, only fast or slow relative to the n it will face.

## When to use / avoid

Reach for this estimate when:
- An input size or constraint is stated up front, and the choice of approach depends on it.
- Deciding whether optimising further is worth the effort.

The estimate is unreliable when:
- Work per step is heavy — network calls, disk reads, or large allocations — since 10⁸ per second assumes cheap in-memory operations.
- n is small enough that constant factors and setup costs dominate the asymptotic term.

## TL;DR

- The penalty for a worse complexity class scales with input size rather than staying a fixed multiplier.
- About 10⁸ simple operations take about one second on typical hardware; this single figure anchors every estimate.
- Multiply the complexity out at the given n, divide by 10⁸, and the result is a rough running time.
- O(log n) is nearly flat across all practical input sizes; O(2ⁿ) and O(n!) collapse past n ≈ 26 and n ≈ 11 respectively.
- Read a stated input size backwards to find the intended complexity: 10⁵ implies O(n) or O(n log n), 3,000 implies O(n²), 20 implies an exponential search.
- The estimate assumes cheap in-memory operations, and breaks down when each step does heavy work.
